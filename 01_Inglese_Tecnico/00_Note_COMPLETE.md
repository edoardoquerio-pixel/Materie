PASSIVE

Why and when do we make use of the passive in English?

Avoid a weak subject and give importance to the concept itself Don’t worry, I have already eaten – You’re right, but I was given a sandwich

Construction: The trick to pass from active into passive is to add the verb to BE in the same tense of the main verb (in this case MAKE) + past participle of the main verb (make – made - made).

Il trucco per passare dall’attivo al passivo è aggiungere il verbo essere allo stesso tempo del verbo principale (in questo caso MAKE) + il participio passato del verbo principale (MAKE - MADE - MADE).

MODAL VERBS (OBLIGATION, ADVICE, POSSIBILITY)

Obligation / Necessity must / have to / need to

Users must change their passwords regularly.

You need to install the latest security patch.

Administrators have to monitor network traffic.

Recommendation / Best Practice Should (Dovrei…)

Companies should implement multi-factor authentication.

Employees should not share login credentials.

Possibility / Risk can/ could/ may/ might

CAN = POSSO, PUOI, PUO’..

COULD / MAY / MIGHT = POTREI, POTRESTI…

This vulnerability could allow remote access.

Attackers may exploit this flaw.

Phishing emails can appear legitimate.

FURTHER NOTES:

-	HAVE TO

La forma 'HAVE TO', da non confondersi con il verbo avere ('TO HAVE') esprime il concetto di DOVERE.

A differenza di 'MUST', che ha solo il presente, può essere coniugato in tutti i modi e tempi proprio come un verbo comune:

Simple Present: HAVE TO / HAS TO - DON'T / DOESN'T HAVE TO - DO /DOES YOU HAVE TO...?

Ex. I have to go to school today

Simple Past: HAD TO - DIDN' T HAVE TO - DID YOU HAVE TO...?

Ex. I didn't have to do my homework

Will: WILL HAVE TO - WILL NOT HAVE TO - WILL YOU HAVE TO...?

Ex. Will you have to buy a new computer?

Present Perfect: HAVE / HAS HAD TO - HAVEN'T / HASN'T HAD TO - HAVE / HAS YOU HAD TO...?

Ex. She has had to go to the doctor

-	DIFFERENZE TRA MUST & HAVE TO / DIFFERENCES BETWEEN MUST & HAVE TO

INFINITIVES & GERUNDS

The infinitive is:

to + base verb

Example: to deploy, to test, to update

In Software English, we use it:

To express purpose

Very common in documentation.

The function is used to calculate totals.

This tool helps to detect memory leaks.

We added logging to improve debugging.

After certain verbs

Common verbs followed by infinitive in technical English:

decide to deploy

need to update

want to refactor

plan to release

forget to commit Example:

Developers need to test edge cases.

She decided to rewrite the module.

GERUND:

A gerund is:

verb + -ing used as a noun

Examples: testing, debugging, logging, monitoring

In Software English, we use:

As the subject of a sentence

Very common in documentation.

Testing is essential before deployment.

Logging improves system traceability.

Refactoring increases maintainability.

After prepositions

If a verb comes after a preposition → use -ing

Common in technical writing:

responsible for updating

interested in learning

used for processing

before deploying

after installing

Example:

This tool is used for monitoring traffic.

She is responsible for maintaining the server.

DON’T KNOW WHETHER TO USE INFINITIVE OR GERUND?

Purpose → use infinitive

Processes/activities → use gerund

Example contrast:

This script runs to back up data. (purpose)

Backing up data prevents loss. (activity as concept)

RELATIVE CLAUSES

Relative clauses give extra information about a noun. They begin with:

who → for people

which → for things

that → for people or things (very common in technical English)

Their structure is usually:

Noun + relative pronoun + clause

Example:

The developer who fixed the bug is on vacation.

The API that returns JSON data is unstable.

The server which handles requests is overloaded.

Defining vs Non-Defining Clauses

Defining (essential information)

No commas. The clause is necessary.

The function that validates input prevents errors.

Users who forget passwords must reset them. Without the clause, we don’t know which function/users.

Non-defining (extra information)

Uses commas. Adds extra detail.

The API, which was updated yesterday, is now stable. The information is additional, not essential.

N.B. In technical writing, defining clauses are much more common.

IMPERATIVES

The imperative form is used for:

Instructions

Commands

Documentation steps

Technical procedures

The structure of the imperative is:

Just the base verb (no subject)

In software contexts it is common in:

Documentation

Install the dependencies.

Configure the server.

Restart the application.

Tutorials / Guides

Open the terminal.

Run the command.

Save the file.

Warnings

Do not delete the production database.

Never expose API keys.

NEGATIVE IMPERATIVE

Structure:

Do not + base verb or

Don’t + base verb

Do not modify this file.

Don’t push directly to main.

Ex. 5 - Noun Stacking (Compound Nouns)

Before starting:

What it is:

Noun stacking happens when two or more nouns are placed together to act as a single noun phrase.
In English, this is very common in technical writing because it compresses information into short, precise expressions.

Structure:

[Noun] + [Noun] (+ [Noun] …)

The first noun(s) describe or modify the last noun, which is the main object.

The last noun is the head of the phrase, the “main thing.”

No articles (“a / the”) are usually used between nouns.

Examples: Data Storage system; Cloud security policy.

How to read them:

Start from the rightmost noun → main thing.

Each noun to the left modifies the main noun.

Often used to make technical writing concise.

Example:

CONTAINER ORCHESTRATION TOOL → a tool (main noun) for orchestrating containers.

Tips

Too long? If there are 4+ nouns, consider using “of” for clarity:

cloud infrastructure provider service → service of a cloud infrastructure provider

Plural nouns usually appear only at the end:

Correct: API request limit

Avoid: APIs request limit

How to order nouns in a stack

Rule of Thumb:

The rightmost noun is the main noun – the “thing” you are talking about.

Nouns to the left act as adjectives – they describe or limit the main noun.

Order modifiers from general → specific: the first noun is more general, the one closer to the main noun is more specific.

Step-by-Step Example

Words: cloud / security / policy

Identify the main noun → What is the “thing”?

policy → yes, the main object.

Decide which noun is more general / which is more specific:

cloud → general context (applies to cloud systems)

security → specific aspect (focuses on security)

Arrange general → specific → main noun:

cloud security policy ✅

Another Example: application / deployment / pipeline

Main noun → pipeline (it’s the thing)

What describes the pipeline? → deployment (type of pipeline)

More general context → application (what is being deployed)

Stack: application deployment pipeline ✅

Quick Tips

Think: “Which noun answers the question ‘what kind of …?’”

What kind of pipeline? → deployment

What kind of deployment pipeline? → application

Context matters – sometimes you reorder for clarity:

database backup solution → solution for backing up databases

backup database solution ❌ sounds odd

Optional adjectives:
Sometimes a noun can act like a regular adjective:

server performance monitoring → monitoring (main) of server performance (modifiers)

Practice makes perfect – start by identifying main noun → most specific modifier → more general modifier.

Ex. 5 - Noun Stacking (Compound Nouns)

Before starting:

What it is:

Noun stacking happens when two or more nouns are placed together to act as a single noun phrase.
In English, this is very common in technical writing because it compresses information into short, precise expressions.

Structure:

[Noun] + [Noun] (+ [Noun] …)

The first noun(s) describe or modify the last noun, which is the main object.

The last noun is the head of the phrase, the “main thing.”

No articles (“a / the”) are usually used between nouns.

Examples: Data Storage system; Cloud security policy.

How to read them:

Start from the rightmost noun → main thing.

Each noun to the left modifies the main noun.

Often used to make technical writing concise.

Example:

CONTAINER ORCHESTRATION TOOL → a tool (main noun) for orchestrating containers.

Tips

Too long? If there are 4+ nouns, consider using “of” for clarity:

cloud infrastructure provider service → service of a cloud infrastructure provider

Plural nouns usually appear only at the end:

Correct: API request limit

Avoid: APIs request limit

How to order nouns in a stack

Rule of Thumb:

The rightmost noun is the main noun – the “thing” you are talking about.

Nouns to the left act as adjectives – they describe or limit the main noun.

Order modifiers from general → specific: the first noun is more general, the one closer to the main noun is more specific.

Step-by-Step Example

Words: cloud / security / policy

Identify the main noun → What is the “thing”?

policy → yes, the main object.

Decide which noun is more general / which is more specific:

cloud → general context (applies to cloud systems)

security → specific aspect (focuses on security)

Arrange general → specific → main noun:

cloud security policy ✅

Another Example: application / deployment / pipeline

Main noun → pipeline (it’s the thing)

What describes the pipeline? → deployment (type of pipeline)

More general context → application (what is being deployed)

Stack: application deployment pipeline ✅

Quick Tips

Think: “Which noun answers the question ‘what kind of …?’”

What kind of pipeline? → deployment

What kind of deployment pipeline? → application

PASSIVE

Why and when do we make use of the passive in English?

Avoid a weak subject and give importance to the concept itself Don’t worry, I have already eaten – You’re right, but I was given a sandwich

Construction: The trick to pass from active into passive is to add the verb to BE in the same tense of the main verb (in this case MAKE) + past participle of the main verb (make – made - made).

Il trucco per passare dall’attivo al passivo è aggiungere il verbo essere allo stesso tempo del verbo principale (in questo caso MAKE) + il participio passato del verbo principale (MAKE - MADE - MADE).

MODAL VERBS (OBLIGATION, ADVICE, POSSIBILITY)

Obligation / Necessity must / have to / need to

Users must change their passwords regularly.

You need to install the latest security patch.

Administrators have to monitor network traffic.

Recommendation / Best Practice Should (Dovrei…)

Companies should implement multi-factor authentication.

Employees should not share login credentials.

Possibility / Risk can/ could/ may/ might

CAN = POSSO, PUOI, PUO’..

COULD / MAY / MIGHT = POTREI, POTRESTI…

This vulnerability could allow remote access.

Attackers may exploit this flaw.

Phishing emails can appear legitimate.

FURTHER NOTES:

-	HAVE TO

La forma 'HAVE TO', da non confondersi con il verbo avere ('TO HAVE') esprime il concetto di DOVERE.

A differenza di 'MUST', che ha solo il presente, può essere coniugato in tutti i modi e tempi proprio come un verbo comune:

Simple Present: HAVE TO / HAS TO - DON'T / DOESN'T HAVE TO - DO /DOES YOU HAVE TO...?

Ex. I have to go to school today

Simple Past: HAD TO - DIDN' T HAVE TO - DID YOU HAVE TO...?

Ex. I didn't have to do my homework

Will: WILL HAVE TO - WILL NOT HAVE TO - WILL YOU HAVE TO...?

Ex. Will you have to buy a new computer?

Present Perfect: HAVE / HAS HAD TO - HAVEN'T / HASN'T HAD TO - HAVE / HAS YOU HAD TO...?

Ex. She has had to go to the doctor

-	DIFFERENZE TRA MUST & HAVE TO / DIFFERENCES BETWEEN MUST & HAVE TO

Al tempo presente, e solo al tempo presente, il verbo 'DOVERE' può essere tradotto sia con il verbo modale 'MUST' che con la forma 'HAVE TO'.

Possono essere utilizzati in maniera indistinta? NO! Ecco quando scegliere 'MUST' e quando ' HAVE TO'.

INFINITIVES & GERUNDS

The infinitive is:

to + base verb

Example: to deploy, to test, to update

In Software English, we use it:

To express purpose

Very common in documentation.

The function is used to calculate totals.

This tool helps to detect memory leaks.

We added logging to improve debugging.

After certain verbs

Common verbs followed by infinitive in technical English:

decide to deploy

need to update

want to refactor

plan to release

forget to commit Example:

Developers need to test edge cases.

She decided to rewrite the module.

GERUND:

A gerund is:

verb + -ing used as a noun

Examples: testing, debugging, logging, monitoring

In Software English, we use:

As the subject of a sentence

Very common in documentation.

Testing is essential before deployment.

Logging improves system traceability.

Refactoring increases maintainability.

After prepositions

If a verb comes after a preposition → use -ing

Common in technical writing:

responsible for updating

interested in learning

used for processing

before deploying

after installing

Example:

This tool is used for monitoring traffic.

She is responsible for maintaining the server.

DON’T KNOW WHETHER TO USE INFINITIVE OR GERUND?

Purpose → use infinitive

Processes/activities → use gerund

Example contrast:

This script runs to back up data. (purpose)

Backing up data prevents loss. (activity as concept)

RELATIVE CLAUSES

Relative clauses give extra information about a noun. They begin with:

who → for people

which → for things

that → for people or things (very common in technical English)

Their structure is usually:

Noun + relative pronoun + clause

Example:

The developer who fixed the bug is on vacation.

The API that returns JSON data is unstable.

The server which handles requests is overloaded.

Defining vs Non-Defining Clauses

Defining (essential information)

No commas. The clause is necessary.

The function that validates input prevents errors.

Users who forget passwords must reset them. Without the clause, we don’t know which function/users.

Non-defining (extra information)

Uses commas. Adds extra detail.

The API, which was updated yesterday, is now stable. The information is additional, not essential.

N.B. In technical writing, defining clauses are much more common.

IMPERATIVES

The imperative form is used for:

Instructions

Commands

Documentation steps

Technical procedures

The structure of the imperative is:

Just the base verb (no subject)

In software contexts it is common in:

Documentation

Install the dependencies.

Configure the server.

Restart the application.

Tutorials / Guides

Open the terminal.

Run the command.

Save the file.

Warnings

Do not delete the production database.

Never expose API keys.

NEGATIVE IMPERATIVE

Structure:

Do not + base verb or

Don’t + base verb

Do not modify this file.

Don’t push directly to main.
